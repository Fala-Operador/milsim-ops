# Regras técnicas do projeto

- Writes: browser never talks to the DB; every write is a server fn in `src/api/*.functions.ts` running services inside `src/server/unidade.server.ts` (one version-checked `apply_changes` RPC). Never call `mutarBase` from components; identity only from the server session. Why: rules/authz run where users can't tamper.
- Reads: per-user "visão" (`src/lib/visao.ts`) is the only read boundary; new collections/sensitive fields are filtered in `visaoParaUsuario` with a test. Pages render after first load (`AuthContext.carga`); re-render via `useVersaoBase()`; API effects depend on `usuario?.id`. Why: browser holds only what the user may see.
- Realtime: every public table is in the `supabase_realtime` publication (pgTAP enforces; add new tables in their migration), but the browser never subscribes to table changes (no policies/grants, so it would get nothing). A trigger on `base_control` broadcasts only the new version on public channel `base`; `src/services/tempoReal.ts` (started in `AuthContext`) refetches the visão when it is newer than `Visao.versao`, with jitter, and screens that ask the server directly use `aoMudarBase`. Why: data still only reaches the browser through the visão rules.
- Schema: migrations in `supabase/migrations/` (unique timestamp, RLS on, no policies, grants to `service_role`, must apply on an empty DB, timestamp later than the last applied one), applied by `.github/workflows/deploy.yml` on push to main (prod) or hml (homologação, its own Supabase project via GitHub Environments) and checked on PRs by `check.yml` (dry-run + pgTAP in `supabase/tests/`); never apply a migration by hand (`db query -f`/psql), and push the file right after a local `db push` (either mismatch makes the deploy reject everything); destructive changes only with approval, guarded by a data check; DB names are English and live only in `src/lib/esquemaBanco.ts` (domain code stays Portuguese); no jsonb columns: nested lists/objects are child tables keyed by the parent PK (+ `position` for lists), declared there; change it and `base_tables()` together (a test compares them). Why: the mapper in `src/lib/persistencia.ts` builds every row and child row from that one map.
- Base cache: the server keeps the last `export_base` per instance and only rechecks `base_control.version` per request (`src/server/unidade.server.ts`). Base tables are written only through `apply_changes` (which bumps the version); SQL that changes their data by hand must also run `update public.base_control set version = version + 1 where id = 1`. SQL functions called by the API never raise SQLSTATE `40001` (PostgREST retries it forever); use `MS409`. Why: a full export costs ~135 ms of DB CPU, and the 40001 loop exhausted the pool at 100% CPU.
- Personal data at rest: columns in `COLUNAS_CIFRADAS` (`src/lib/esquemaBanco.ts`) are stored AES-256-GCM encrypted by `src/server/cifraDados.ts` (decrypt after `export_base`, encrypt the lote right before `apply_changes`; key `PERSONAL_DATA_ENCRYPTION_KEY`, server env only); uniqueness via blind indexes in `INDICES_CEGOS`. New personal fields go in that list; SQL never filters, checks or indexes those columns; anything else calling `apply_changes` must encrypt with `cifrarLote`. Why: DB, backups and Realtime only ever see ciphertext; losing the key loses the data.
- User free text becomes HTML only via `src/lib/regras.ts` (escapes first).
- Domain rules live in one pure module each: home eligibility `src/lib/divulgacao.ts` (admin writes `src/services/divulgacao.ts`); modalities `src/lib/modalidades.ts`; ticket/coupon availability `src/lib/vendas.ts`; location `src/lib/localizacao.ts` (geocoding in `src/services/geolocalizacao.ts`, coords never stored); theme `src/contexts/ThemeContext.tsx` (pre-paint script mirrors it); event editor steps/review `src/lib/eventoEditor.ts`; event WhatsApp contact `src/lib/contatoEvento.ts` (number public, group link only for confirmed registrants and event managers, filtered in the visão); finance movements tabs/filters `src/lib/movimentacoes.ts`; event lifecycle (auto-conclusion after `fimEm`) `src/lib/cicloEvento.ts`, applied by `src/server/unidade.server.ts` on every write and on the first read after an event ends (no scheduled jobs). Why: one place decides each rule.
- Analytics only via `src/services/analytics.ts` → `src/api/analytics.functions.ts`, revalidated in `src/server/analytics.server.ts`; formulas in `src/lib/analytics.ts`.
- Ticket payments (Stripe Checkout): rules in `src/lib/pagamentos.ts` (reservation, what holds a seat, visão masking) and `src/lib/stripe.ts` (webhook signature, event → action); base state changes in `src/services/inscricoes.ts`; Stripe HTTP calls only in `src/server/stripe.server.ts` (fetch, no SDK) orchestrated by `src/server/pagamentos.server.ts`, always outside `mutar`; Stripe webhooks hit the Supabase Edge Function `supabase/functions/stripe-webhook` (holds the `whsec_` secrets, verifies, forwards signed with `STRIPE_WEBHOOK_FORWARD_SECRET`) and then `src/routes/api.stripe.webhook.ts`, which only trusts that internal signature. Platform fee lives in `platform_settings` (admin page `/admin/pagamentos`), read via `taxaDaPlataforma`. Capacity counts `ocupaVaga` (confirmed + live reservations); finance counts confirmed only. Without `STRIPE_SERVER_API_KEY` registrations confirm directly. Organizer payouts use Connect destination charges to accounts created via Accounts v2 (`POST /v2/core/accounts`, recipient + Express dashboard; v1 account creation is blocked in live for new platforms) and otherwise used through v1 endpoints: account status rules in `src/lib/repasses.ts` (also masks `organizacao.recebimento` in the visão), base writes in `src/services/repasses.ts`, API in `src/api/repasses.functions.ts`; destination and fee are fixed on the reservation, and refunds of transferred sales reverse the transfer and the fee. Connected-account balance/payouts are read live (`Stripe-Account` header, 60 s server cache, never stored or in the visão); embedded components (`src/components/PaineisStripe.tsx`, needs `STRIPE_BROWSER_PUBLIC_KEY`) cover onboarding, notification banner and account management (opened by a button) so organizers never leave the site; balance and payouts are shown from the server read, not Stripe components. Disputes live in `pagamento.disputa`. Sales metrics come from inscrições via `resumoVendas` in `src/lib/analytics.ts`. Why: `mutar` may re-run its function, so external calls there would charge or refund twice.
- Check-in: rules in `src/lib/checkin.ts`; `src/services/checkinStore.ts` keeps server base and offline IndexedDB queue separate. Why: offline rules testable, storage never mixes.
- Operator profile: grants/vouchers only via `recalcularProgressao` (`src/services/progressao.ts`, idempotent); others' profiles only via `montarPerfil`. Invoices live in private `documentos` bucket, owner-only signed URLs, never in the visão.
- UI components are shadcn/ui primitives in `src/components/ui/*` (restyled to the app identity; `cn` lets caller classes win); `src/components/ui.tsx` only holds composites (`Campo`, `Modal`, `EstadoVazio`, skeletons, `ErroSecao`, `Spinner`). Custom-styled clickables use `Button variant="plain" size="none"`; no new raw `<button>`/`<input>`/`<select>`/`<table>`/dialogs; confirmations and notices use `useConfirmacao()` (`src/contexts/ConfirmacaoContext.tsx`: `confirmar`/`avisar`), never `window.confirm`/`alert`/`prompt` (free-text answers use `ModalTexto`). Why: one component library, same look.
- Carousels share `SectionCarousel` (scoped scrollbar suppression).
- Admin (`/admin`) and organizer (`/organizacao`) areas navigate only through `LayoutMenuLateral` (`src/components/MenuLateral.tsx`): grouped side menu from `lg`; below `lg` the same sections appear at the top of the header's ☰ sheet (via `useMenuArea`) and the page shows only a breadcrumb; new sections go into a group there, with `contador` for pending items. Never add a second menu button in the page. Why: 10+ sections don't fit top tabs; on mobile two menus confused users.
- Status labels use shared nonwrapping `Badge` (`@/components/ui/badge`) with fixed-size SVG icons; registration and attendance use `StatusInscricao`. Why: labels stay intact across tables, cards and detail views.
- Event editor drawer (`src/components/editorEvento/`): no `<form>`, buttons `type="button"`, backdrop never closes; drafts autosave to server, non-draft edits stay in IndexedDB until "Salvar alterações". Why: closes only on explicit action; public data not overwritten early.
- Event image crops commit their generated pixels in the crop interaction, never in a delayed step effect. Why: navigation must not cancel pending image generation.
- Support desk: admin-only triage; rules in `src/lib/suporte.ts` (access, per-user `vistaDoChamado`, encaminhamentos, derived "aguardando organizador" status, and `linkSuporte`/`resolverLinkSuporte` as the only builders of support URLs), writes in `src/services/suporte.ts` via `src/api/suporte.functions.ts`; message audience lives in each message (`canal`, `encaminhamentoId`), organizers see only their forwards and explicitly shared attachments; responsible/solution/link derive from immutable "sistema" messages (no new columns); attachments in private `documentos` bucket under `suporte/`. Why: schema can't change without DB access, internal talk must never reach participants, and notification links must resolve per viewer.
- Event boosting: rules in `src/lib/impulsionamento.ts` (derived status, eligibility, stable ordering, one card per event); writes in `src/services/impulsionamentos.ts` via `src/api/impulsionamentos.functions.ts`; sections merge campaigns before curation inside `eventosDaSecao`; campaigns are never deleted. Why: one place decides who appears where, history is preserved.
- Pre-event missions: rules in `src/lib/missoes.ts` (window, scoreboard = average per confirmed member + team-goal bonus, ranking, season, army prize); writes in `src/services/missoes.ts` via `src/api/missoes.functions.ts`; the secret code never reaches participants (stripped in the visão); points stay with the submitter's army at submission time; scoreboard/season are server-computed reads that must not go through `chamar` (applying the visão bumps the version used as query key → refetch loop). Why: fair scoring, no leaked answers, no data of other players in the browser.
- General community (Twitter-like feed and user forums, `/comunidades`): the ONE exception to base/visão. `social_*` tables stay OUT of `base_tables()` (an everyone-sees-everyone feed can't ship whole to every browser); reads are paginated by the SQL functions `social_posts_page()` / `social_forums_page()`, which apply visibility (public profile, approved follower, blocks, forum membership) in the DB; writes go straight to `social_*` from `src/server/social.server.ts` with the session identity, via `src/api/social.functions.ts` (reads return DTOs, not through `chamar`). Rules in `src/lib/comunidadeGeral.ts` (220 chars, 4 photos, rate limit; `podeVerAutor` mirrors the SQL rule); moderation only through `moderarTexto` in `src/lib/moderacao.ts` (term list now, AI later behind the same signature). Only the profile preference (`users.social_private`) and notifications live in the base. New social data follows this pattern, never the base. Why: the base export and the visão would grow with every post and every browser would receive all of them.
- Docs: business rules in `docs/regras-de-negocio.md`, flows in `docs/fluxos.md`, one page per API in `docs/api/<módulo>/<api>.md` (+ index `docs/api/README.md`). Changing a rule, an API's input/permission/errors, or adding/removing an API updates its page in the same change. Why: the docs list exact error messages and permissions, so they go stale silently.
